# GEMS Parity & Reproduction Specification

Authoritative, pinned specification for **every** GEMS benchmark figure: the exact
dataset (with byte-identity proof), model flag (`-m`), seed, `-ninit`, binary, and the
**matched baseline** each GPU result is compared against. This is the artifact the parity
red-team audits, and the reproducibility statement for the thesis §Methods.

**Parity principle.** A GPU-vs-X comparison is admissible only when GPU and X are matched on
all five axes: (1) dataset **bytes** (md5-identical, not merely "same name"), (2) model
mode (`-m MF` / `-m MFP` / single model — identical on both sides), (3) `-seed`, (4)
documented thread/rank layout, (5) binary provenance. Any unmatched axis is called out
explicitly as a caveat, never hidden.

## 4. The `-m` mode parity rule (defect found + fix)

**Defect (in the original CTF energy harness `run_ctf_1m_mf_energy.sh`).** It runs the GPU
at **`-m MF`** (full set, *includes* +R FreeRate) but prints the CPU baseline as
**`-m TEST`** walls (`np2=3076.9 … np16=1122.4`). `-m TEST` excludes the +R/+I+R candidates,
so the GPU is being credited for a larger search than the CPU it is timed against — an
**apples-to-oranges** comparison that inflates the speedup.

**Fix (enforced here).** For every CTF-vs-CPU figure the CPU side runs the **identical `-m`
mode** as the GPU: `-m MF` GPU ↔ `-m MF` CPU (FCA), `-m MFP` GPU ↔ `-m MFP` CPU (FCA). The
FCA `-m MF`/`-m MFP` scripts already evaluate the full candidate set including +R, so they
are the correct baseline. `-m TEST` numbers are retired from the comparison.

## 5. Energy + SM-utilisation methodology

Matched instrumentation so GPU and CPU energy are measured on the same basis (per
`ref_gadi_fullnode_and_rapl_energy`):

- **GPU energy — PROBE RESULT (job 172800779, H200 driver 580.126.20):**
  `total_energy_consumption` is **NOT SUPPORTED** on this H200/driver — the hardware integrator
  is unavailable. Therefore GPU energy = **trapezoidal integration of `power.draw` sampled at
  0.2 s** (not the old 2 s rectangular, which mis-estimates the bursty JOLT kernels). Report a
  sensitivity check at 0.2 s vs 0.5 s to bound the sampling error, and state explicitly in the
  figure that no hardware energy counter was available (methodological honesty).
- **GPU SM-utilisation — PROBE RESULT:** DCGM `dcgmi` is installed but the **nv-hostengine is
  not running in-job** (`unable to connect to host engine`), so SMACT/SMOCC (fields 1002/1003)
  are unavailable unless a job first launches `nv-hostengine`. Plan: attempt `nv-hostengine &`
  then `dcgmi dmon -e 1002,1003` in the energy job; **if that fails**, fall back to
  `nvidia-smi dmon -d 1 -s pucm` (the `sm` column, confirmed working at 1 s) and label the axis
  "utilization.gpu proxy (% time ≥1 kernel active), not true SM occupancy". nsys/ncu ARE
  available (`/apps/cuda/12.5.1/bin`) for a separate small-input profiling pass.
- **CPU energy.** Intel RAPL `/sys/class/powercap/intel-rapl:*/energy_uj` (a true cumulative
  integrator, so sample rate cannot lose energy), **per-domain wrap-corrected** (pkg ~262 kJ,
  dram ~65.7 kJ wrap independently — correct by the smallest non-negative a·PKG+b·DRAM), pkg +
  DRAM domains. **Summed across ALL nodes** via a per-node sampler launched on every rank host
  (mpirun -rf rankfile), NOT head-node-only — the existing `run_fca_energy_aa1m.sh` already
  does this correctly and is the template. **Whole-node allocation is mandatory** (RAPL sums
  the whole socket regardless of tenant → a shared node contaminates energy).
- **Profiler separation (accuracy rule).** nsys / ncu / Linaro `perf-report` add 5–30 %
  sampling overhead → they run on a **separate profiling pass on a small input**, NEVER on the
  energy- or wall-timed run. The timed run carries only the light samplers (dmon @ 1 s, RAPL @
  5 s, `total_energy_consumption` deltas). The FCA scaling wall (fig 9) is measured by pure
  `date`-bracketing of `mpirun` with `perf-report` REMOVED from the timed invocation (it only
  profiles the head node on multi-node anyway).
- **Hashara (external OpenACC).** We do **not** possess her binary, so her energy/SM numbers
  are **cited** from her report (H200: AA-1M tree search ~90 min; AA-100K MF stage ~28 min).
  For an *algorithm* comparison we run **her exact command** (`-seed 1 -ninit 2 -optalg
  2-BFGS`, no `-nt` → 1 thread, no `-m` → full MFP) with **our** JOLT on the same H200 and
  the same byte-identical alignment, and label the axis honestly: **OpenACC directive port
  (hers) vs hand-written CUDA + JOLT joint optimiser (ours)** — different implementation
  *and* different algorithm. No claim that the two were run on identical silicon unless the
  GPU model string in both logs matches.

## 10. Log collection & evidence policy (for moderator review + thesis provenance)

**Problem this solves:** `/scratch/rc29` is purged on a rolling window — that is exactly how the
raw logs for figs 1/2/6/7/8 were lost before archival. Therefore **every reproduction job's raw
logs are copied to the durable, non-purged `/g/data/um09` archive**, checksummed, and indexed.

- **Archive root:** `/g/data/um09/as1708/gems-provenance/reproductions/<label>_<jobid>/`, each with
  `SHA256SUMS.txt`; a top-level `INDEX.md` lists every harvested job. Moderators verify integrity
  with `sha256sum -c SHA256SUMS.txt` inside any run dir.
- **Harvester:** `setonix-iq/gadi-ci/gems/gems_harvest.sh <run_dir> <label> <jobid>` — idempotent,
  copies **light evidence only** (`*.log`, `*.stdout`, `*.console`, `*.iqtree`, `*.treefile`,
  `*.ckp.gz`, `rapl_*`, `power*.log`, dmon, rank logs, the PBS `.o<jobid>`, the submitted script)
  and **excludes** the 96 MB alignments / GB build trees (alignments are provenanced by md5 in §1,
  not re-stored). Verified 2026-07-01 (test on `repro_hashara_171999649`: 3 logs archived, 10 MB
  `.phy` correctly skipped).
- **Belt + suspenders:** (belt) each GEMS job adds `gdata/um09` to `-l storage` and calls the
  harvester as its **last step, on PASS *and* FAIL** (a failure log is evidence too — the avian
  SIGTERM at walltime is itself a finding); (suspenders) a login-side harvest sweep after the
  campaign re-runs the harvester over every run dir as a backstop before any scratch purge.
- **Self-cleanup is subordinate to evidence:** the build/src-tree `rm -rf` in the build scripts
  runs **only after** logs are harvested to `/g/data`, and never deletes a `.log`/`.o`/`.iqtree`.
- **Provenance flip:** on each figure's completion, `FIGURE_PROVENANCE.md` flips PURGED → reproduced
  with the real job ID and the archive path, so every headline number is traceable to a raw log a
  moderator can open.

## 11. FCA feasibility wall — CPU `-m MF`/`-m MFP` does NOT complete at 1M (audit a34d3de1)

The SU-waste audit + `CHANGELOG.md` (jobs `169332780/781/783/785/786/788/791/792`, corroborated by
`Docs/results.md`) establish: the FCA MPI ModelFinder (`iqtree3-mpi-fca-ws-a2`) running the FULL
`-m MF`/`-m MFP` candidate set (incl +R FreeRate) at **1M sites has NEVER completed** at np=1/2/4/16
— every run wall-killed/cancelled at 1.5–3.5 h with no result. Root cause: the `filterRatesMPI`
global-barrier straggler + the `+F+I+R5` FreeRate tail on the rank-0 critical path (one +R5 model at
1M = 1800–3100 s; rank 0 must clear ~14–30 serial models before the pruning broadcast fires). The
**only** 1M config that completes is `-m TEST` (np16 ≈ 1122 s MF / ~40 min total), which **excludes** +R.

**This is not just a limitation — it is a RESULT.** The GPU CTF completes the full `-m MF` (with +R)
at 1M where the CPU MPI implementation cannot at any practical node count → a **capability** argument,
stronger than a raw speedup. Feasible CPU baselines: (a) `-m TEST` at 1M (1/2/4/16 scaling curve),
(b) `-m MF`/`-m MFP` at 100K (completes ~1300 s, all np). The driver now HARD-REFUSES `-m MF`/`-m MFP`
at 1M for NODES<8 (exit 11) so a doomed combo cannot burn a full wall for zero data.
